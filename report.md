# Детальный Анализ Проекта

В данном отчете представлен глубокий аудит кодовой базы, архитектуры, безопасности и производительности приложения на основе стека Next.js, Redux Toolkit и Drizzle ORM.

## 1. Полное и детальное ревью проекта
Проект представляет собой современное веб-приложение с разделением на клиентскую (публичную) часть и панель администратора.
- **Стек технологий**: Next.js 14/15 (App Router), React, Redux Toolkit (с RTK Query), Tailwind CSS, компоненты Shadcn/UI, Drizzle ORM, PostgreSQL, MinIO для хранения медиа.
- **Мультиязычность**: Реализована кастомная система локализации, управляемая через базу данных (`system_texts`), что позволяет изменять переводы прямо из админки.
- **Структура**: Проект хорошо структурирован. Логика роутов Next.js, работа с базой данных и бизнес-логика разнесены по разным слоям.

## 2. Архитектура приложения
Архитектура приложения построена на классическом 3-уровневом паттерне (Controllers -> Services -> Repositories).
- **Плюсы**: Отличное разделение ответственности. Слои сервисов изолированы от прямого взаимодействия с ORM через репозитории, что делает код чистым и упрощает тестирование.
- **Внедрение зависимостей (DI)**: Реализован ручной DI-контейнер в `src/modules/core/container.ts`.
- **Архитектурный изъян**: В `container.ts` происходит инициализация подключения к БД (`drizzleDatabase.connect`) и инициализация бакета MinIO (`initializeBucket`) на уровне выполнения (загрузки) модуля. В среде Next.js (serverless) глобальные сайд-эффекты на верхнем уровне модуля — это плохая практика. При Hot-Reload (в разработке) или Cold Starts (на сервере Vercel/AWS) это может приводить к утечкам подключений (Connection Leaks) и "падениям" приложения по тайм-ауту соединения. Подключение к БД следует реализовывать через Singleton-инстанс с пулом соединений (например, `postgres`), кэшируемый в глобальном объекте.

## 3. Ошибки, неконсистентные данные и скрытые баги
- **Критический баг с авторизацией (Mismatch payload)**: 
  При логине (в `dev-login/route.ts` и `refresh/route.ts`) JWT токен подписывается со структурой: `signToken({ userId, role: "admin" })`. 
  Однако функция проверки `getUserId` в `src/utils/auth.ts` пытается получить ID пользователя иначе: `return payload?.id as string | undefined;`. 
  В результате переменная `id` всегда `undefined`, и все защищенные API-роуты не могут корректно идентифицировать пользователя.
- **Бесконечный цикл в категориях**: 
  Таблица `categories` имеет поле `parentId`, ссылающееся само на себя. На уровне схемы и контроллеров не обнаружено проверок на цикличные зависимости. Если категория А станет родителем категории Б, а категория Б — родителем А, рекурсивная сборка дерева категорий "положит" бэкенд из-за переполнения стека (Maximum call stack size exceeded).
- **Конфликт состояния RTK Query и React State**: 
  На публичной странице `src/app/[locale]/(public)/page.tsx` запросы уходят через RTK Query (`useGetPostsQuery`), но при пагинации (Infinite Scroll) новые посты подмешиваются в локальный React-стейт: `setPosts((prev) => [...prev, ...newPosts])`. Это ломает философию Redux: при любой инвалидации кэша в Redux локальный стейт массива постов не обновится корректно, что приведет к дубликатам элементов в UI или отображению удаленных постов.

## 4. Уязвимости (логин, токены)
- **Клиентская "псевдо-защита" админ-панели**: 
  В файле `src/app/admin/layout.tsx` проверка доступа к админке реализована через React `useEffect` и чтение `localStorage.getItem("admin_logged_in") === "true"`. Это означает, что защита выполняется *на стороне браузера клиента*. Любой посетитель может открыть DevTools, установить этот флаг в `localStorage` и получить визуальный доступ ко всем разделам админ-панели (даже если API отклонит запросы данных). Маршруты админки должны быть защищены через **Next.js Middleware**.
- **Дефолтный JWT Secret**: 
  В `src/utils/jwt.ts` используется фоллбэк: `process.env.JWT_SECRET || "default_super_secret_key_change_me_in_prod"`. В случае сбоя CI/CD или ошибки в `.env` файле, приложение выйдет в прод с публично известным секретом, что позволит любому выпустить себе токен администратора.
- **Слишком агрессивная эвристика Refresh Token**: 
  В `refresh/route.ts` есть "Advanced Theft Detection" (Premature Refresh): если кто-то пытается запросить refresh токен, когда старый access токен еще жив (осталось > 2 минут), система отзывает вообще *все токены пользователя* (revokeFamily). В SPA-приложениях с множеством открытых вкладок или при обрыве сети параллельные запросы могут случайно вызвать refresh. Это приведет к массовым ложным срабатываниям и постоянным разлогинам реальных пользователей.

## 5. Перформанс БД и связей (Drizzle)
- **Полное отсутствие индексов**: 
  В `src/repositories/drizzle/schema.ts` не определено ни одного индекса (отсутствуют `.index()`). Фильтрация по внешним ключам (например, `collectionId`, `categoryId`) и по статусу (`status`) при большом объеме данных будет вызывать тяжелый Sequential Scan базы данных.
- **Катастрофическая просадка при поиске по JSONB**: 
  Локализованные поля `title` и `description` хранятся в формате JSONB. При текстовом поиске в `postRepository.ts` происходит следующее: `sql\`\${posts.title}::text ILIKE \${'%' + query.search + '%'}\``. 
  Это заставляет базу данных "на лету" преобразовывать JSONB всех записей в текст и искать по подстроке. Это крайне ресурсоемкая операция. Необходимо использовать GIN-индексы и JSONB-операторы Postgres (например, полнотекстовый поиск или оператор `@>`).
- **Проблема Overfetching при запросе списков**: 
  Репозиторий `postRepository.ts` во всех методах (включая `getAll` для пагинации) использует метод `this.getWithRelations()`, который жадно подтягивает (JOIN) `poster`, `collection`, `category` (вместе с ее `color`, `collection` и `parent`), теги и всю медиа-галерею проекта. Это приводит к передаче огромного количества избыточных данных из БД в Node.js просто для отображения карточек в сетке.

## 6. SEO и семантика публичных страниц
- **Сломанная семантика навигации категорий**: 
  В публичной `page.tsx` навигация по категориям реализована на элементах `<button>` с обработчиком `onClick={() => router.push(...)}`. Поисковые боты (Googlebot) не нажимают на кнопки и не исполняют сложный JavaScript для перехода между страницами. Следовательно, страницы отфильтрованных категорий **никогда не будут проиндексированы**. Необходимо переписать фильтрацию с использованием нативных тегов `<a>` (через компонент `<Link>` от Next.js).
- **Слаги проектов не оптимизированы для SEO**: 
  В роутинге детальной страницы `projects/[slug]/layout.tsx` переменная `slug` по факту передает `id` проекта (UUID формата `123e4567-e89b-...`), так как в коде вызывается `getPostById(slug)`. Для хорошего SEO URL должен содержать читаемый текст (например, `/projects/handmade-wooden-toy`), а не UUID.
- **Плюсы в SEO**: 
  Функция `generateMetadata` для детальной страницы проекта написана превосходно. Имплементированы OpenGraph теги, Twitter Cards, `alternates` для мультиязычности и генерация превью-картинок. Однако, `keywords` извлекаются из тегов напрямую, что хорошо, но стоит следить за тем, чтобы теги не были пустыми для конкретной локали.
