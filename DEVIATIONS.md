# Plan vs. Code Deviations

Source of truth is the **current code in `src/`**. Plans in `docs/project-plan/` are treated as intent, not as spec. Each item is tagged:

- **[intentional]** – the code chose a different but valid approach; nothing to fix, the plan is just outdated.
- **[quality]** – the code diverges from the project's own design rules (`CLAUDE.md`'s Working Agreements, `docs/guidelines/*`, layered architecture, contracts) and is a candidate for cleanup.
- **[gap]** – planned, not implemented.
- **[added]** – exists in code, absent from the plans.

Stack choices (Next.js route handlers instead of Express, Drizzle + Postgres, Redux Toolkit) and the `/api/v1` prefix are **not** deviations; see `CLAUDE.md`.

Verification scope: all of `src/app/api`, `proxy.ts`, controllers/services/repositories (read in full or in the relevant parts), schema + migration, storage, store, i18n, public pages, admin layout/login. Admin CRUD pages and UI components were skimmed structurally, not line by line.

## Backend

### Architecture
- **[intentional]** Planned Express + a central error middleware + `authMiddleware` → Next.js route handlers, `src/proxy.ts` (the Next 16 name for middleware) for auth, and a `try/catch → sendError()` block repeated in every controller method.
- **[quality]** Planned "all business logic in Services". Actual:
  - `src/app/api/v1/auth/**` (Google exchange, refresh rotation, theft detection, dev-login, logout) holds full business logic and talks to repositories directly. There is still no `AuthService` class, but the token-mint/hash/cookie-setting block that used to be copy-pasted three times is now one shared `issueSession()` (`utils/authSession.ts`, fixed 2026-10-02, second round) — the remaining per-route logic (OAuth code exchange, theft-detection heuristics, the allowlist re-check) is genuinely route-specific, not duplicated.
  - **[fixed 2026-10-02, second round]** `CategoryService` (`deleteCategory`) and `MediaService` (`deleteMedia`) used to import `drizzleDatabase` + schema tables and run queries themselves, bypassing the repository interfaces. They now call repository methods instead (`CategoryRepository.countChildren`, `PostRepository.countByCategory`/`countByPoster`/`countGalleryUsage`), each guarded against a non-UUID input the same way `getById` is.
  - `collections/[id]/posts/route.ts` and `posts/[id]/comments/route.ts` contain logic (query rewriting, response shaping) instead of delegating.
- **[quality]** Storage: plan requires an Adapter/Strategy interface so the backend can swap Local/S3/Cloudinary. Actual: concrete `StorageService` writing to a local media folder directly (MinIO was removed 2026-11-12), no interface. `MediaService` imports the singleton.
- **[fixed 2026-09-23]** `initializeBucket()` was imported in `container.ts` but never called, so the bucket had to be created by hand. Now `ensureBucket()` (`minioClient.ts`) runs before the first upload of a process: it creates the bucket if missing and sets public read only when the bucket has no policy. `initializeBucket()` is removed.
- **[intentional]** DI is manual in `src/modules/core/container.ts` (repositories → services → controllers). Repositories are module-level singletons.

### Auth
- **[intentional]** Plan: access token in header. Actual: both tokens in HttpOnly cookies (`accessToken` path `/`, `refreshToken` path `/api/v1/auth`, SameSite=Strict, `Secure` only when `NODE_ENV=production`). RTK Query `baseQueryWithReauth` does the silent refresh on 401.
- **[intentional]** "Single hardcoded admin email" → `ADMIN_EMAILS` (comma list). The user row is auto-created with a placeholder password (`"admin_hashed_password"`), set directly by `auth/google/exchange/route.ts` via `userRepository.save()` — it never goes through `UserService`. A manual-creation path (`POST /users` → `UserService.saveUser`, same placeholder) existed briefly but was removed 2026-10-01 as unused (see "Routing / API surface" below), so the Google-login route is now the only place a `users` row is created.
- **[fixed 2026-10-02]** The allowlist used to be checked only once, at the Google-login exchange step: `proxy.ts`, `isAdminRequest()` and `getUserId()` all verified JWT signature/expiry/role only, so a token kept working even after its email was removed from `ADMIN_EMAILS`, until the 7-day refresh chain ran out. The access token now carries `email`; a new `verifyAdminToken()` (`utils/jwt.ts`) checks signature, `role === "admin"` and that the email is still in `ADMIN_EMAILS`, and all three call sites use it. `auth/refresh/route.ts` also re-checks the user's email on every rotation and revokes the family if it's no longer allowed. A token issued before this change has no `email` claim and is rejected, but upgrades transparently through one ordinary refresh (the "premature refresh" heuristic below explicitly treats a token `verifyAdminToken` would reject as not suspicious, so it falls through to normal rotation instead of a forced logout).
- **[intentional]** Refresh tokens: session table + hash + `isUsed` + `tokenFamily` rotation and reuse detection, as planned.
- **[added]** "Premature refresh" heuristic: refreshing while the access token has >2 min left revokes the whole family. Not in the plan, and it can log out a legitimate admin (multi-tab, retries).
- **[added]** `status=all` sentinel in `utils/postVisibility.ts` → `resolveStatusFilter` (2026-09-28), not in the plan: the admin dashboard's explicit signal that it wants every post status. With a valid admin token it resolves to no filter; without one it throws `UnauthorizedError` (401) instead of the usual silent narrowing to `Published`, so an expired dashboard session now triggers the normal silent-refresh-or-redirect flow instead of quietly showing a partial list.
- **[fixed 2026-09-28]** `GOOGLE_CALLBACK_URL` was a required env var but unused (its local value was a placeholder). Since 2026-09-23 the redirect address is fixed on the server as `NEXT_PUBLIC_APP_URL` + `/admin/login` and the client no longer sends it; since 2026-09-28 the var is no longer required (`env.ts`).
- **[added]** `POST /auth/dev-login` bypass, gated by `NEXT_PUBLIC_DEV_MODE` and, since 2026-09-19, refused when `NODE_ENV=production`.
- **[added]** OAuth code flow with `state` and PKCE (S256), since 2026-09-23: `POST /auth/google/start` builds the Google URL and keeps both values in a single-use HttpOnly cookie (`oauthState`, SameSite=Lax, path `/api/v1/auth`); `google/exchange` checks them, sends `code_verifier`, and verifies the ID token with `jwtVerify` against Google's keys (RS256, issuer, audience = `GOOGLE_CLIENT_ID`, expiry) and requires `email_verified`. The old `GET /auth/config` (exposed the client id) was removed. Code: `utils/googleOAuth.ts`.
- **[quality]** Auth endpoints differ from the plan (`sign-in`/`sign-out`/`refresh` → `google/start` + `google/exchange`/`logout`/`refresh`). That is fine; see the routing note below.

### Routing / API surface
The endpoint table in `backend.md` stays valid as a target. Differences in the code:
- **[intentional]** Resources live at `/api/v1/<resource>` (no `/admin/` segment); protection is by HTTP method in `proxy.ts` (all `POST/PUT/PATCH/DELETE` need a valid JWT, except public `POST /posts/:id/comments`; since 2026-09-19 every method on `/api/v1/users/**` and `/api/v1/admin/**` needs one too). Only admin comment moderation is under `/api/v1/admin/comments`.
- **[intentional]** Updates use `PUT` (not `PATCH`), except `system-texts/:id` and `admin/comments/:id/status`.
- **[intentional]** `GET /collections/:collection_slug/posts/:post_slug` is not implemented; posts are fetched via `GET /posts/:slugOrId`, and `resolveId()` lets most routes accept either UUID or slug.
- **[intentional]** Filters: `?category=` takes comma-separated slugs/UUIDs, `?inStock=true` (plan: `?in_stock`), plus `?collection=` and `?status=`. `?search=` matches **title and description** (fixed 2026-10-05, previously title only — matches the plan now).
- **[gap]** `/admin/slugs` and `/admin/localization` from `diagram.jpg`: no Slug or Localization tables/endpoints. Localization is served by `/system-texts` (UI strings) and by JSONB fields on entities.
- **[added]** `PUT /categories/reorder`, public comment endpoints, `/admin/comments/*`, `/system-texts/*`.
- **[fixed 2026-09-28]** Access was decided by HTTP method in `proxy.ts`, not by resource, so every `GET` outside `/users/**` and `/admin/**` was public — including `GET /media`, which listed every file, also images of unpublished posts. Fixed 2026-09-19: `/api/v1/users/**` and `/api/v1/admin/**` need a JWT for every method, `UserRepository` no longer returns `password`, and anonymous readers get only `Published` posts (`GET /posts`, `GET /posts/:slugOrId`, `GET /collections/:id/posts` and the project page metadata). Fixed 2026-09-28: `/api/v1/media/**` joined the same pattern in `proxy.ts` (B12); its only consumer in the codebase is the admin media picker. See `PRODUCTION-READINESS.md` → "Fixed in code".
- **[fixed 2026-10-01]** `POST/PUT/DELETE /api/v1/users` had no role model beyond "any valid JWT" and zero consumers in the admin UI; removed entirely, along with `UserService.saveUser`/`deleteUser`, `IUserService`'s matching signatures, and the now-unused `userSchema`. Only `GET /users` and `GET /users/:id` remain, under the same JWT gate as before.

### Response and error contracts
- **[intentional]** `{data, meta}` / `{data:{}, error:{code,message,details}}` and the `BaseError` hierarchy (`serialize()`, `errorCode`, `statusCode`) match the plan.
- **[quality]** `sendError()` used to return the **raw `error.message`** for non-`BaseError` failures (Drizzle messages include the SQL and parameters). Fixed 2026-09-19: the response is the generic `InternalServerError`, details go to the log only.
- **[fixed 2026-10-02, second round]** Invalid UUIDs and malformed JSON used to end in 500 instead of 4xx. A malformed JSON body is now a clean `ValidationError` (400, new `parseJsonBody()` in `utils/validateRequest.ts`); a non-UUID id now short-circuits to "not found" in every repository's `getById`/`getByIds`/`delete` instead of reaching Postgres. `status`/`search` query values are unaffected by this fix and remain unvalidated against an enum/pattern.
- **[quality]** `meta.totalItems` is the size of the current page (`services/pagination.ts`), not the total, and there is no total-count query. Plan contract implies the real total.
- **[quality]** `GET /collections/:id/posts` double-wraps (`data: {data, meta}`) and reports `totalItems: undefined`. `/auth/dev-login` returns `{error: "string"}` outside the contract.
- **[quality, partly fixed 2026-10-02 second round]** 40 `console.*` calls bypass the winston logger the plan mandates. 6 server-side ones are now `logger` calls (`refresh`, `tagService`, `sitemap`, `projects/[slug]/layout.tsx`'s metadata catch; the Google login routes already used the logger since 2026-09-23). The remaining ~34 are all inside `"use client"` components (admin pages, `CommentSection.tsx`, `combobox.tsx`): winston is a Node-only library and cannot run in the browser, so these need a separate client-safe logging decision, not a straight swap — tracked in `CHANGE-PLAN.md` CP-18.
- **[fixed 2026-09-28]** `CommentService.replyToComment` threw a plain `Error("Parent comment not found")` for a missing parent (surfaced as a generic 500); it now throws `NotFoundError` (404).
- **[fixed 2026-10-01]** `CommentService.createComment` let a nonexistent `postId` reach Postgres and surface as a raw FK-violation 500; it now checks `postRepo.getById(postId)` first and throws `NotFoundError` (404). `replyId` still has no existence check **and no FK constraint at all** (see "Database & Migrations" → self-referencing links below) — a different, quieter gap: a bogus value is silently stored rather than rejected.
- **[fixed 2026-10-02]** The `replyId` gap above is closed at the application level: `createComment` now also checks `commentRepo.getById(replyId)` when one is given and throws `NotFoundError`. The schema gap is unchanged — `comments.reply_id` still has no FK constraint, so this is an app-level check, not a DB-level one.

### Media
- **[quality]** Plan: convert everything to JPG; thumbnail 300×300, original 1200×1200 fitted. Actual: format preserved (JPEG/PNG only), original max 1000×1000, thumbnail max 320×320 (`fit: inside`). The WebP branch in `StorageService` is unreachable because uploads allow only JPEG/PNG.
- **[fixed 2026-09-28]** MIME check used to use only the client-supplied `file.type`, with `sharp` re-encoding as the only real validation (a bad file surfaced as an uncaught 500). `StorageService.uploadImage` now decodes with `sharp(buffer).metadata()` first and uses the real `format` (only `jpeg`/`png`) to pick the encoding branch, the stored extension and the object `Content-Type`; an unsupported or undecodable file is a `ValidationError` (400). Stored `orientation` is still lowercase (`"landscape"`), while the type/Zod enum is `"Portrait" | "Landscape"` (unrelated, still open).
- **[fixed 2026-09-23]** Public URLs were built from `S3_ENDPOINT` (the address the server connects to, an internal host in Docker) and stored absolute in the DB. They now come from the required `S3_PUBLIC_URL`: `${S3_PUBLIC_URL}/${bucket}/${object}`. They are still stored absolute, so changing that variable later needs a SQL `replace()` on `media`. `MediaService.deleteMedia` used to leave the two objects in the bucket, and `S3_FORCE_PATH_STYLE` was required but unused; both fixed 2026-09-28 (`StorageService.deleteImage()`, and the env var dropped from `requiredEnvVars`).
- **[fixed 2026-10-02]** `MediaService.uploadMultiple` had no cap on the number of files in a single multipart request. Now capped at `MAX_FILES_PER_UPLOAD` (optional env var, default 50) — rejected with a `ConflictError` before any file is processed. The admin media library already uploads one file per request, so this only affects a request built directly against the API.
- **[gap, found 2026-10-02, declined 2026-10-06]** Next's `experimental.proxyClientMaxBodySize` is not set in `next.config.ts` (defaults to 10 MB) and silently truncates any request body over that for every route behind `proxy.ts`, before `NEXT_PUBLIC_MAX_FILE_SIZE_MB`'s own check runs. Confirmed: a single file at/over ~10 MB, or two files together exceeding it in one request, get truncated mid-file and fail with a raw 500 instead of a clean "file too large" error — and a file right at the configured 10 MB cap is at real risk of this because of multipart framing overhead. Not hit today since the admin UI uploads one file per request and real photos are smaller; the owner declined the `next.config.ts` fix 2026-10-06 on that basis (`CHANGE-PLAN.md` CP-16).
- **[intentional]** Integrity check on delete (blocked when used as poster or gallery item) is implemented as planned.

### Data consistency on delete
- **[intentional]** Plan: background task to strip tag/category ids from posts. Actual: relational join tables with `ON DELETE CASCADE` (`posts_to_tags`, `categories_to_tags`, `posts_to_media`), plus service-level guards: a category with children or posts → 409; a media item in use → 409. `TagService.deleteTag` additionally rewrites categories (redundant with the cascade).

- **[intentional]** `TokenSession.expiresAt`: Unix number in the plan → `timestamp` column.
- **[added]** `posts.created_at` (used for manual ordering via date override), 17 btree indexes on FKs/status. The old audit claim "no indexes" is obsolete.
- **[quality, declined 2026-10-06]** Self-referencing links are **not** real FKs: `categories.parent_id` and `comments.reply_id` have no constraint in schema or migration. Application-level guards exist (`CategoryService.saveCategory` checks for self-reference, cycles, and — since 2026-10-05 — that `parentId` actually exists; `CommentRepository.delete` removes replies manually; `CommentService.createComment` checks `replyId` exists); the real DB-level FK constraint was discussed with the owner 2026-10-05 and declined 2026-10-06 as unnecessary on top of the app-level checks (`CHANGE-PLAN.md` CP-22).
- **[quality, partly fixed 2026-10-05]** No GIN/trigram index. Search runs `title::text ILIKE '%…%'` OR'd with the same pattern on `description` (since 2026-10-05, previously title only — still a sequential scan on both columns).
- **[fixed 2026-10-01]** `%`, `_` and `\` in the search term are now escaped before being wrapped in the `ILIKE` pattern (`postRepository.ts`), so a literal wildcard character is matched literally instead of acting as a SQL wildcard.
- **[fixed 2026-09-28, superseded 2026-10-01]** `users.password` is `NOT NULL`. `UserService.saveUser` used to never set it, so `POST /users` for a new user could not succeed; it briefly set the same placeholder string the Google login route uses. On 2026-10-01 `POST/PUT/DELETE /api/v1/users` (and `saveUser`/`deleteUser`) were removed entirely as unused dead code, so the Google-login exchange route (which sets the same placeholder directly via `userRepository.save()`) is now the only path that creates a `users` row — the underlying "no real password flow" design gap is unchanged. `seeds/initial-data/users.json` carried a committed password-shaped value too; deleted 2026-10-02 (unused by any loader, see "Routing / API surface" above and `PRODUCTION-READINESS.md` → Secrets management).
- **[intentional]** One migration file (`0000_tired_human_robot.sql`, 13 tables, journal has one entry). Nothing calls `migrate()` at startup and there is no `db:migrate` script; `test:infra:start` uses `drizzle-kit push`.
- **[quality]** Seeds: only `system-texts.json` has a runner (`runSystemTextsSeed.ts`, not wired into `package.json`). `categories`, `categories_to_tags`, `collections`, `colors`, `tags`, `users` JSON files have no loader in the repo. `pull-system-texts.js` writes to a stale path (`src/migrations/initial-data`, real: `src/migrations/seeds/initial-data`).
