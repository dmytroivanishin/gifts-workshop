### CP-37 · Admin list GETs' `Cache-Control` can hide an admin's own write for up to 60s (found 2026-11-02)
- `GET /api/v1/categories`/`collections`/`tags`/`colors` send `Cache-Control: public, max-age=60` unconditionally (CP-23, 2026-10-12). The browser's own HTTP cache honors that for RTK Query's post-mutation refetch too (`fetchBaseQuery` is a plain `fetch()`, no cache-busting) — so after an admin creates/edits/deletes/reorders one of these 4 entities, the same tab can keep showing the pre-edit list for up to a minute even though the write already succeeded and the data layer is correct.
- Found while building `tests/e2e/admin/categories-reorder.spec.ts` (CP-31 phase 3): a verified-200 reorder `PUT` left the on-page row order unchanged 2s later; confirmed via a direct, cache-independent API re-read that the server-side `order` values were already right. CP-23's own writeup flagged this exact trade-off only for `system_texts`/`posts` ("a write can leave a client-side cached read up to 60s stale... a deliberate, minor trade-off") — it didn't anticipate that categories/collections/tags/colors share the same unconditional caching and get hit on every ordinary admin edit, not just a rare content change.
- **Need:** a decision, not a reflexive fix — options include: `cache: "no-store"` on these 4 GETs specifically (loses the Cache-Control benefit entirely), a short-TTL or `private` cache instead of `public, max-age=60` (weakens CP-23's original intent), or accepting it as-is as the same kind of trade-off CP-23 already named (an admin can always hard-refresh). Not on the active queue until you weigh in.

### CP-33 · Strict, nonce-based CSP (not urgent, revisited 2026-10-06)
- The baseline CSP (`next.config.ts`, added 2026-09-28) keeps `script-src`/`style-src` `'unsafe-inline'` because App Router RSC streaming and framer-motion inline styles need it. A stricter CSP needs a per-request nonce generated in `proxy.ts`, forces every page into dynamic rendering (no static generation/ISR/CDN caching), and `style-src` likely stays `'unsafe-inline'` anyway (framer-motion mutates the `style` attribute directly, which a nonce doesn't cover) — a real architecture change, not a config tweak.
- Checked 2026-10-06: `grep` across `src/` finds zero uses of `dangerouslySetInnerHTML` or `innerHTML` — React escapes all rendered content by default, so there is currently no known injection point for an attacker to get a `<script>` onto the page in the first place. `'unsafe-inline'` today is a dormant defense-in-depth gap, not an active, exploitable hole; it would start to matter if a future change adds something that renders raw HTML (a rich-text comment field, a markdown renderer, a third-party widget). Owner's call: not worth the static-rendering trade-off while that's hypothetical — kept as a low-priority "needs a plan" item, not declined outright, revisit if the app ever grows an HTML-rendering surface.

- **CP-51 · Admin real-time correctness fixed (CP-37 resolved) + server-side caching for categories/collections/tags/colors/system-texts/posts with cross-entity invalidation (2026-11-08).** Raised as part of a 10-point batch ("при удалении категорий, тегов и тп они не удалюятся вообще, или удаляется один а потом остальные нет... при создании и редактировании любых сущностей они не добавляются и не редактируются на лету"). Root cause (confirmed by a dedicated investigation, not assumed): this was exactly the already-documented, not-yet-fixed **CP-37** — `categories`/`collections`/`tags`/`colors` GETs sent `Cache-Control: public, max-age=60, stale-while-revalidate=300` unconditionally (CP-23), and RTK Query's plain `fetch()` refetch-on-mutation could be served that stale body straight from the browser's own HTTP cache instead of ever reaching the server — explaining both "create/edit doesn't appear" and "one delete works, others don't" (each of the 4 entities has its own independent cache window, so they go stale/fresh out of sync with each other). No second bug existed in `useDeleteConfirm`, any mutation's `invalidatesTags`, or media's bulk-delete path (media was never affected — it never had a `Cache-Control` header at all). "Needs a full restart, not just a refresh" was a false correlation — restarting takes long enough for the 60s window to lapse on its own; nothing here needed a process restart.
  **Fix, in the direction the owner actually wanted (clarified live, mid-fix):** not simply "remove admin's cache" — the owner's explicit framing was "admin can be whatever you think is right, real-time matters most there; **public cache is important and can be made long** (he first suggested 2h–24h for categories/colors/etc and half a day for posts, then explicitly swapped it: posts are the more dynamic content, so posts should get the **shorter** duration and categories/tags/colors/etc the **longer** one) — but it's critical that invalidation is instant and identical for every visitor when something is added or changed, not dependent on whose browser happened to cache what and when." A long browser `max-age` alone can never satisfy that (HTTP caching is pull-only, per-browser, with no server-initiated invalidation) — so the real fix has two parts:
  1. **`categoryController`/`collectionController`/`tagController`/`colorController`/`systemTextController`** now compute `cacheSeconds` per-request via `(await isAdminRequest()) ? undefined : CACHE_SECONDS.lookup` — the exact pattern `postController` already used for posts — so a valid admin session (on *any* page, including the public site viewed in the same logged-in browser) always gets a fresh, uncached response, while a genuine anonymous visitor gets the cacheable one.
  2. **A real, server-side cache now backs the data itself**, not just the HTTP header: `categoryService`/`collectionService`/`tagService`/`colorService`/`postService` each wrap their list/by-id reads in `unstable_cache` and call `revalidateTag(..., { expire: 0 })` on every write — the exact pattern already proven for `system_texts` (CP-26), just extended to these 5. This is what actually makes "invalidated the same way for everyone, instantly" true: the server's own answer is correct the moment any admin writes, regardless of what any browser has cached, so a long `Cache-Control` duration on top of it is safe rather than a staleness risk.
  **Cross-entity invalidation, worked out from what each entity actually embeds via a live join** (checked in code, not assumed): `PopulatedCategory` embeds a live-joined `color` (not tag content, only bare `tagsIds`) — so categories' cache entries are tagged `["categories", "colors"]`, meaning `colorService`'s own `revalidateTag("colors")` call also flushes the categories cache in the same call, with zero extra code in `colorService`. `PopulatedPost` embeds live-joined `category` (itself embedding `color`/`collection`), `collection`, `tags`, and `poster`/gallery `media` — so posts' cache entries are tagged `["posts", "categories", "collections", "tags", "colors"]`, meaning every one of the other 4 services' existing `revalidateTag` calls also flushes the posts cache automatically; media was deliberately left out of that list since `MEDIA_IN_USE` already blocks deleting a media row referenced by any post, so a live post's embedded media data can never go stale this way. `collections`/`tags` embed nothing mutable from elsewhere, so their own tag is enough. **A real, previously-dormant correctness gap found and fixed along the way**: `postService.syncCategoryTags` (auto-adding a post's tags to its category's `tagsIds` on create/update) writes to `categoryRepo` directly, bypassing `categoryService.saveCategory` entirely — so this specific write was never revalidating the categories cache at all until a `revalidateTag("categories", { expire: 0 })` call was added right after it; verified live (below) that this was a real, reproducible gap, not theoretical.
